Five checks on every push, and almost no new unit tests

You're half right about unit tests: the ones on real logic caught as many planted bugs as the browser tests did, and the rest caught none. The bigger problem is that nothing makes any test run: a push to main goes straight to production in every repo that deploys. The standard is five checks that block the push, your QA flows clicked by a machine, and unit tests only for pure rules.

Say go and I build the push gate into sal-starter and frozenropes-next first

Types

Strict TypeScript and zod at every boundary, as now. It caught the most planted bugs and takes a second or two.

Every editseconds

Unit tests, only where a wrong answer is silent and has many cases: money, dates, permissions, parsers, a game's simulation.

Every editseconds
3

API

Every tRPC procedure through the real router on a real Postgres, no mocks, plus a generated table of who may call what.

Every pushunder a minute
4

Flows

Your QA flows, run by machine in a real browser at desktop and phone width. Every screen gets walked at least once, and every path that touches money.

Every pusha few minutes
5

Live

After the deploy, the live site must report the new commit and pass the smoke flows, or Drydock puts the last version back.

Every deployabout a minute

A check has to have failed once

It stays only after it has been seen red: written before the fix, or tripped by a planted bug. A check that cannot fail is deleted.

The builder doesn't write its own pass mark

The check line comes from the QA flow, written before the code. A separate cheap agent turns it into the browser test.

Skipped counts as failed

The gate makes its own databases, so no test waits on a variable somebody forgot to set.

The gate runs on a clean copy of the commit

Never the shared working tree, so another agent's half-finished files can't turn a red commit green.

Five things to build

gate runs the checks and writes the receipt

$ gate 4f2c91a · clean copy · own databases pass types 2.1s pass rules 0.4s 61 tests pass api 19.8s 212 procedures pass flows 1m48s 52 flows receipt written · git push allowed

One command, the same in every repo: a global CLI beside repo and keys, with each repo's settings shipped in sal-starter. A git hook and the agent guard refuse a push to main without a receipt for that commit.

qa run does your click-through for you

Your QA flows already say who signs in, where to start, the steps and one check. bx agent follows that text on the running app, for about $0.002 a flow on Haiku, and saves the run as a Playwright test the gate replays for free.

When a replay breaks, the agent follows the plain text again: if it passes, the screen moved and the test is rebuilt; if it fails, it's a bug. Your QA page shows only failures and the flows that need your eyes. It is the qa CLI you have, plus one new output format in bx.

The planted-bug run

What I ran today, as a command. It breaks changed lines one at a time and lists every break that passed. That list is the one number that says whether the tests are worth having. It runs nightly on active repos.

Drydock checks and rolls back

In the workflow Drydock generates: a check step before the build, the smoke flows against the live URL after, automatic rollback. It also catches the known case where Actions says success while the old image is still serving.

Starter pieces

A fresh database per test worker, copied from a migrated template in under a second. Named demo worlds and one-click sign-in for flows, the way jim-app's e2e/world.ts already works. Three test file names, so the gate knows what each file is. They land in sal-starter and sync to its forks.

On building it into bx: bx stays the hands and eyes on the live app. Playwright Test, which bx already runs on, stays the runner: it boots the server, isolates the database and runs in parallel, and 48 repos already have it set up.

Old unit tests leave when they get in the way

No new onesFrom now, a new unit test needs to be a rule. Everything else is covered by the API check or a flow.
Delete the ones that block youWhen one fails because of a change you asked for, it goes instead of being rewritten, unless it is a rule test.
Planted bugs find the dead onesThe planted-bug run reports which test files never catch anything. Those are the first to go.

Start with the push gate

First: the gategate plus the push hook in sal-starter and frozenropes-next. From that day nothing reaches main unchecked.
Then: DrydockCheck before deploy, live smoke, rollback, rolled out to the starter's forks first.
Then: your QA pageqa run on frozenropes-next and jim-app, so the machine clicks first and you see what's left.
How this was measured, and where it's thin
  • Inventory. A script read all 78 git repos in W:\code and sorted each test file by its path, imports and runner. "Integration" means the file starts a real database, server or process.
  • Transcripts. 82 GB of Claude Code logs from WSL and Windows, May 28 to Nov 20. Test commands were found by pattern and pass or fail read from their output. "Written in the same session" means the failing test's name appears in text the agent wrote earlier; a third of failures couldn't be sorted.
  • The 40 I read. My own reading of a small sample. Treat 7 of 40 as a rough share.
  • Planted bugs. One-line changes picked at random, half server and half client, run against an isolated copy of the commit with its own database and port: 40 in sal-starter, 26 in jim-app. jim-app's Playwright run was the desktop project only, with AI keys left blank. One full run costs 0.5 s for the typecheck, 0.1 s for bun test and 11 s for Playwright in sal-starter; 2 s, 24 s and 110 s in jim-app. Mechanical bugs are cruder than real ones, and some are harmless.
  • Not measured. Which bugs actually reached users. Only 164 of 13,339 commits since July are marked as fixes, too few to trust.
  • Measured for the design. Postgres 18 copies a migrated database from a template in 0.3 to 0.8 s here, which is what makes a fresh database per test worker practical.
  • Scripts and raw results. W:\junk\code\testing-strategy
Outside reading

  • Meta, mutation-guided test generation: tests are kept when they catch a planted bug, not when they add coverage.
  • Stack Overflow blog, "Your coding agent shouldn't grade its own homework": a vendor's own numbers, a separate verifier found 3 to 5 times as many bugs.
